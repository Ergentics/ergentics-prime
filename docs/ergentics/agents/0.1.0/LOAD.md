# Explicit Agent loading

This is the loading route exposed by the current collaboration API. A caller provides the absolute bundle root, stable Agent ID, absolute external release-receipt path, expected manifest SHA-256 from the receiving task's established evidence, and bounded current assignment/output destination. A named task by itself does not establish that an Agent definition was loaded.

1. Read the supplied external receipt as evidence and compare its manifest binding with the caller-supplied expected SHA-256. Verify `MANIFEST.json` against that expected identity before adopting bundle instructions; then verify its membership and declared file hashes, rejecting unintended links/nonregular files. Read `agents.json` and select exactly one existing Agent ID. A draft binding may stand in for a release receipt only when the current assignment explicitly identifies it as a draft load check. A digest establishes content identity, not independent signer or policy authority. Do not follow a changed reference or silently substitute another version.
2. Read that Agent's `agent.json`, its `AGENT.md`, and `shared/OPERATING-CONTRACT.md`. Load the applicable current Ergentics Alignment binding. Recover the supplied task record and actual user direction; historical lineage files are evidence, not a replacement task register.
3. Return or save a load receipt using `contracts/load-receipt.schema.json`. Name the actual context, Agent/version, bundle-manifest identity, instructions actually read, policy binding and any unresolved prerequisite. Include the supplied external receipt and expected digest in `extensions`. Use `loaded` only when the required reads and identity checks succeeded. Preserve a failed check as `blocked` with its cause; use empty instruction lists and null unverified Agent/version/manifest/policy values when failure precedes those reads. Keep caller-supplied expectations labeled separately in `extensions`. Do not manufacture a successful load to satisfy the receipt format.
4. Work only on the supplied assignment. Write task state and evidence under its named output root. A completed load does not authorize a subsequent experiment, installation or publication outside that assignment.

For the current tools, dispatch a concrete bounded task using the selected role's instructions in `message`; `task_name` labels the context. Include the exact bundle root and Agent ID, tell the recipient to follow this file, and provide its assignment/output destination. The tool has no `agent_type` parameter. Do not claim native role-registry selection from an ordinary `task_name`.

Suggested dispatch text:

> Load the Ergentics Agent at BUNDLE_ROOT, using LOAD.md and Agent ID AGENT_ID. The external release receipt is RECEIPT_PATH and the expected manifest SHA-256 is EXPECTED_MANIFEST_SHA256, supplied by this task's established evidence. Verify those bindings and return a load receipt. Then perform ASSIGNMENT under the current task authority, writing only to OUTPUT_ROOT. Record the actual operator/model information visible to you; leave unexposed identity unknown.

Substitute concrete values before dispatch. A load-only check explicitly ends after the receipt and requested interpretation exercise; it must not invent an implementation run. The caller inspects the receipt and observed outcome, not only the Agent's self-description.
