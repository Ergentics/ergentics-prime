# Prime Root Analysis: custody and launch readiness

Method revision 1.0.0. Ergentics, LLC owns the originating method. Use this
reference for a requested source/history replay or consolidation. It supplements
Research Custody and Prime's actual contracts; it does not create a new gate.

## Establish lineage and preserve local work

Identify each Git database, worktree, commit/tree and selected overlay. Record
the accessible graph root separately from declared donor/research lineage.
Follow concrete project references to earlier app repositories or retained
evidence. Do not call a first accessible commit the inception of every method.
Remote tip equality establishes the compared refs at the observation time;
it does not prove deleted history, a complete remote object census or durability
of this task's uncommitted package.

Inventory tracked edits, untracked and ignored first-party source, generated
artifacts, and inaccessible/excluded paths separately. Preserve selected deltas
with their path, base/blob, mode, stable byte identity and readback before
integration. A broken Git pointer limits Git lineage; surviving source can still
be preserved. Retain missing registrations rather than pruning them to improve
the inventory. Stored paths, unique bytes and running instances remain different
counts. A large generated directory is not evidence of thousands of helpers.

Exclude credential and raw-history paths before body intake. A tool returning
only path/status output may still inspect content internally. Record the actual
tool and scope; do not turn a filename-only rendering into a no-read guarantee.
Summarize large manifests by asserted schema fields and bounded counts. Inspect
the full saved records locally as needed without dumping build caches or paths
indiscriminately into the conversation.

## Reconcile semantics before selecting an overlay

Compare a local delta against its own base, then against the maintained
equivalent. Exact blob equality proves byte equality. Lack of equality does not
prove unique functionality. For project serialization, compare parsed objects;
keep meaningful target, build-setting and launch-action changes visible.

Disposition each variant as selected implementation, inherited/replaced work,
retained historical proposal, or an explicit unresolved choice. Name the actual
invariant at issue. Do not stop at a generic recommendation to review when that
review is authorized and feasible. Preserve optional unfinished features and
unadmitted successor contracts outside the selected active overlay. Do not
delete, reset, stash or merge them blindly to manufacture a clean tree.

A safety-motivated change to frozen ingress, acceptance, descriptor or attempt
semantics can still be a protocol amendment. Classify every selected material
change as IMPLEMENTATION_FIX, INSTRUMENTATION_FIX, PROVENANCE_FIX or
PROTOCOL_AMENDMENT. Hold a protected amendment before dependent execution;
continue authorized source review and ordinary repairs. A commit hold blocks
commits, and an old-runtime hold blocks its activation, within their actual scope.

## Repair custody without changing historical outcomes

Resolve a missing relative locator against the declared original project before
claiming evidence is lost. Compare exact source and artifact identities. Add an
explicit locator or selected portable snapshot with original paths/hashes and
collection identity. Do not silently relabel copied records as native outputs
of the receiving tree. Preserve historical bytes and distinguish their phase
from later development. Retain source/image objects as data without activating
old helpers or regenerating an experiment to reconstruct its evidence.

## Qualify each family and exact candidate

Use a matrix with candidate identity, authority contract, historical observation,
current evidence, missing prerequisite and next permitted operation. Driver V2,
static bootstrap, fixture identity, app/archive, VM and Rust families may share
gate letters while having different predicates and authority. A PASS-like
receipt in one family must not satisfy another family's prerequisite.

Source identity, compilation, signing, installation, profile loading, runtime
entry, output correctness, terminal cleanup and scientific admission are
separate claims. Materialization or READY_FOR_SEPARATE_APPROVAL with zero live
entries is not a boot result. A historical no-boot record also cannot describe
every later phase: inspect the relevant later receipt before a broader claim.

For a new operation bind exact source/overlay, inputs, toolchain/runtime,
protocol, attempt identity, resource envelope, expected evidence and applicable
authority before outcomes. Preserve requested versus observable model/backend
properties. No automatic scientific retry or toolchain substitution is created
by this replay. Prepare concrete source/qualification prerequisites before asking
for the remaining exact gate decision.

Use LOCAL_DURABLE -> COMMITTED -> PUSHED -> REMOTE_SHA_VERIFIED literally for
each new package. A local manifest or older remotely verified branch does not
satisfy repository durability for newly gathered work.

## Extend from reviewed outcomes

Preserve failed calls, incomplete reviews and corrections in the post hoc
analysis. Harvest a focused reviewed lesson with its limitation and counterexample,
using the existing bounded Auto Harvest control. It does not imply continuous
collection, policy amendments or automatic installation of later revisions.

[Root Analysis golden cases](root-analysis-golden.json) cover these decisions.
When independent review is authorized, supply scenarios and minimum evidence
without expected criteria; record actual responses and score them separately.
The cases are interpretive, not executable malware or scientific gate tests.
Keep policy, method, package, record schema, Agent/profile, corpus and runtime
versions distinct. Extend this reference and cases only for demonstrated gaps.
