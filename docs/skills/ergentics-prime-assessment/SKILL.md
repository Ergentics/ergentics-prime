# Ergentics Prime Assessment

Produce a source-bound assessment and the authorized repairs, while keeping
unexamined surfaces visible. Ergentics retains originating ownership and method
authority. This skill supplies a review method; it is not policy authority,
execution permission, a malware detector, or a deployed monitor.

## Recover the task and its coverage

Use the installed Ergentics Alignment binding when the task adopts that policy.
Recover the existing task record, latest user direction, maintained repository
and HEAD, local changes, original evidence, authorization and holds. Continue
work already authorized. Keep this task separate from other tasks' registers.

Define the actual completion question and required surfaces before claiming an
exhaustive result. [The surface profile](references/prime-v2-surfaces.json)
provides the Prime/V2 starting point; extend it when a caller, dependency,
different executable name or installation adds a surface. It is not a fixed
filename allowlist or a statement that every installation has these files.

Select required surfaces from the current question. Skill installation readiness
and source-only maintenance do not require a whole-machine process census.
Preserve an unavailable count as unknown; revisit it only when it matters to
the requested conclusion. Do not carry an earlier exhaustive scope into a new,
narrower task by default.

Record one disposition for every discovered item, including inaccessible and
excluded items. Deduplicate bytes for analysis while preserving path, inode,
version and managed/unmanaged-copy distinctions. Add newly discovered scope to
the inventory; preserve the earlier snapshot and label the correction.

For a requested inception-to-current replay or consolidation, use
[the Root Analysis custody/readiness flow](references/root-analysis.md). Map
the selected source and local deltas to their own qualification families;
matching gate letters, successful historical receipts and preserved drafts
do not establish a shared current verdict. This mode extends the named project
scope through concrete lineage leads; it does not require a workstation census.

## Follow execution and ownership

Start with entrypoints and follow their imports, native bridges, generators,
image paths and immediate callers. Review normal, timeout, partial-spawn,
failed-observation, failed-signal, pipe and cleanup paths. A deadline checked
before a slow callback is not a check immediately before spawning. Cleanup of
an owned child may need its own bounded budget after execution authority ends;
that budget must not renew on retries or authorize new work.

Distinguish bounded iteration, expected test-fixture waiting, and indefinite
recovery. Check the caller's actual containment before relying on an outer
timeout. A byte cap does not bound waiting for EOF. A source guard does not
update a retained image or stop an already running process.

Inspect stored images as data. Do not invoke unknown or old helpers to discover
their behavior. An OS-denied census stays unavailable; do not substitute another
API to bypass it. Preserve unknown running counts and the exact denied surface.
Follow the Behavior Review method when interpreting adverse or malware claims.

## Repair and verify

Preserve useful current functionality. Fix demonstrated lifecycle and intake
defects. When the user has authorized retirement of obsolete helpers, reject
before their old intake and side effects, covering applicable import and worker
entrypoints. Preserve historical bodies and evidence separately; name retained
source, binary, cached and live copies outside the stop. Do not infer authority
to delete them, disable unrelated services or replay a frozen experiment.

Bind checks to the exact changed source and, where relevant, built image.
Use discriminating synthetic cases and a working benign control. For rejection
boundaries, consider full/broken output, open input, alternate startup routes
and an already-expired deadline. Preserve initial failures and corrected runs.
Keep historical gate acceptance separate from new regression results. Run only
tests and operations within the current authorization.

When independent models are authorized, give each a concrete partition and raw
evidence. Reconcile their findings against the files and tests. Record their
configured identities and review scope; agreement is not execution evidence.

## Durable record and extension

Maintain the existing task report plus an assessment record using
[the record contract](references/assessment-format.md). Use
`scripts/validate_assessment.py RECORD.json --check-files` to check record
consistency and current file identities. The utility validates supplied metadata;
it neither discovers omitted scope nor proves the truth of observations.

Before stopping, record completed work, unresolved items, exact candidate
identities, test limits, active holds and the next authorized action. An empty
search, a pattern scan, all-green tests or a successful metadata validator is
not an exhaustive assessment. A required unavailable surface prevents an
unqualified completion claim.

Keep this package's source in the repository. Change `metadata.version` and
`references/changelog.md` together when behavior or record semantics change. Keep record
schema versions separate from package and policy versions. Add surface entries
and evidence types without silently redefining existing claims; incompatible
record changes need a new schema version. Preserve issued packages and their
hash manifests. Respect the task's commit/publication hold.

For a requested lesson harvest or extension, use
[the harvest and extension method](references/harvest-and-extension.md) and
[reviewed lesson lineage](references/lesson-lineage.json). Select one lesson
domain and its reviewed evidence; preserve observation, decision, limits and a
counterexample. Auto Harvest prepares a bounded local package when authorized.
It does not mean continuous collection or automatic installation of revisions.

For installation-readiness review, use
[the readiness distinctions](references/install-readiness.md). Exercise
[the golden cases](references/golden-cases.json) with
`scripts/test_golden_cases.py`; these complement the record validator's tests.
Give interpretation scenarios without answer criteria to an independent reviewer
when that review is authorized and useful. Keep executable results, authored
expectations and observed agent responses separate.

For packaging, use the [shared metadata procedure](references/metadata-validation.md)
and declared PyYAML range. Record the actual interpreter, module and validator
identity; do not install a dependency merely because one invocation lacks it.
Distinguish source preparation, local installation, app discovery and Git
publication. Validate the exact package before installation when authorized.
